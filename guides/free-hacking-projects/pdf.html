Free Hacking Home Lab Workbook

Ten connected projects that build one hacking home lab for free: a honeypot that catches real attackers, your own VPN, a hacking range, an Active Directory lab, a security operations center and more.

Version 1.0 · November 2026 · For your own devices and legal practice targets only

Read this first. Every project in this workbook runs on systems you own or on targets built for practice. Keep lab targets on a private network that cannot reach the internet, keep your real server logins separate from the honeypot, and never point any of these tools at a system you do not have written permission to test.
How to use this workbook. The ten projects build one home lab. Projects 1, 2, 5, 6 and 9 run on a free cloud server; projects 3, 4, 7, 8 and 10 run on your own PC. Do them in order the first time, because later projects reuse earlier ones. Each project lists what you need, the steps, what you should see, what to do if it breaks, and what you learned.

1Catch real hackers with a honeypot and an attack map

Time: one evening, plus one night of waiting. You learn: Linux, SSH, cloud firewalls, logs, basic Python.

What you need

  • An Oracle Cloud Free Tier account. Oracle asks for a card to verify your identity; Always Free resources are not charged.
  • A free MaxMind account for the GeoLite location database.

Steps

  1. Create an Always Free virtual machine running Ubuntu. Use the Arm (Ampere A1) shape, which allows up to 2 OCPUs and 12 GB of memory. Add your own SSH public key when you create it.
  2. If you see "out of host capacity", choose another availability domain or try again later. This is a temporary shortage, not an error on your side.
  3. Log in over SSH. Move your real SSH login to an unusual port and allow keys only, so the honeypot can take port 22 without exposing your real login.
  4. Install Cowrie as a normal (non-root) user, following the official installation guide. Cowrie listens on port 2222; redirect port 22 to it as the guide describes.
  5. Allow incoming traffic on port 22 in the instance's security list and in the server's own firewall.
  6. Leave it running overnight.
  7. Read Cowrie's JSON log. The event reference explains each event: login attempts, the usernames and passwords tried, and the commands typed.
  8. Build the map: download the GeoLite2 City database, write a short Python script that reads the attacker IP addresses from the log, looks up each location in the database, and plots the points on a map with a mapping library such as Folium. Save it as an HTML file and open it in your browser.

What you should see

  • Login attempts within minutes to hours, common username and password pairs, download commands for malware, and points on your map from many countries.

If it breaks

  • No connections at all: check that port 22 is open in both the security list and the server firewall, and that Cowrie is running.
  • You locked yourself out: use the instance console in the Oracle dashboard to fix your SSH settings.

You just learned

  • How exposed services get found automatically, what attackers do after logging in, how cloud firewalls work in layers, and how to turn raw logs into a visual.

Keep this server. Projects 2, 5, 6 and 9 build on it.

2See everything your phone sends with your own VPN and Pi-hole

Time: one to two hours. You learn: VPNs, DNS, Docker, port forwarding.

What you need

  • The server from Project 1 and Docker Engine.

Steps

  1. Install Docker on the server.
  2. Run wg-easy, following its getting started guide. It gives you a WireGuard VPN and a web page for managing devices. (The older PiVPN project was discontinued in 2024.)
  3. Open only the VPN's UDP port in your security list. Keep the wg-easy web page private, for example reachable only through the VPN itself.
  4. Run Pi-hole in Docker on the same server, following the Pi-hole documentation.
  5. Set wg-easy's DNS server to Pi-hole's address, so every device on the VPN uses Pi-hole.
  6. Create a client in wg-easy, scan the QR code with the WireGuard app on your phone, and connect.

What you should see

  • Pi-hole's dashboard filling with every domain your phone looks up, including tracking and analytics domains, with blocked requests counted.

If it breaks

  • Connected but no internet: check that the VPN's DNS points at Pi-hole and that Pi-hole is running.
  • Never expose Pi-hole's DNS port to the whole internet. An open DNS resolver gets abused by attackers.

You just learned

  • How a VPN tunnel works, how DNS turns names into addresses, how containers run services side by side, and how much data apps send in the background.

3Build your own hacking range

Time: an evening. You learn: virtualization, isolated networks, scanning, web testing.

What you need

  • A PC with at least 8 GB of RAM, VirtualBox, the Kali Linux virtual machine, Metasploitable 2 and OWASP Juice Shop.

Steps

  1. Install VirtualBox and import the Kali virtual machine.
  2. Create an internal network in VirtualBox and attach Kali and Metasploitable to it. Metasploitable is deliberately vulnerable: it must never be reachable from the internet.
  3. Run Juice Shop inside the lab, for example with Docker on Kali.
  4. Take a snapshot of every machine before you start.
  5. From Kali, discover the targets and their open services with Nmap.
  6. Route your browser through Burp Suite Community and explore Juice Shop's requests. Its first challenge is finding the hidden score board.
  7. For each service on Metasploitable, note its name and version and research known weaknesses. Write down how you would get in before you try.

What you should see

  • A list of services and versions, the Juice Shop score board ticking off challenges, and notes on which services are outdated.

If it breaks

  • Restore the snapshot. That is what it is for.

You just learned

  • How to build a safe lab, how scanning reveals a machine's attack surface, how web traffic looks through a proxy, and how to research a target methodically.

4Break into a fake company network

Time: a weekend. You learn: Windows domains, Active Directory, attack-path thinking.

What you need

  • A PC with around 16 GB of RAM or more for the smallest lab, plenty of free disk space, and GOAD (Game of Active Directory) by Orange Cyberdefense. Its Windows machines use free evaluation licences.

Steps

  1. Read GOAD's installation guide and pick the smallest lab your PC can run.
  2. Install it on an isolated network. The lab is intentionally full of misconfigurations and must stay off the internet.
  3. Join your Kali machine to the same isolated network.
  4. Start as a normal domain user and collect information about the domain with BloodHound.
  5. In BloodHound, find a path from your user to a domain administrator, and work through each step of it.

What you should see

  • A graph of users, groups and computers, and at least one path from a low-privileged user to full control of the domain.

If it breaks

  • Installation failures are usually memory or disk space. Try the smaller lab or close other programs.

You just learned

  • How companies manage Windows users, why one misconfiguration can expose a whole network, and how attackers think in paths rather than single bugs.

5Lock down your real server

Time: one hour. You learn: Linux hardening, firewalls, automated blocking.

Steps

  1. Disable password logins and root login for SSH, and use keys only.
  2. Close every port you do not use, both in Oracle's security list and in the server's firewall. Keep only the honeypot, your SSH port and the VPN port.
  3. Turn on automatic security updates.
  4. Install CrowdSec with its firewall bouncer, so detected attackers are blocked automatically.
  5. After a day, list CrowdSec's decisions to see which addresses it blocked and why.

What you should see

  • A growing list of banned addresses, most of them the same kind of automated scanners your honeypot recorded.

If it breaks

  • Locked out after a firewall change: use the Oracle instance console to undo it.

You just learned

  • The basics every server needs, why defaults are dangerous, and how shared blocklists protect everyone who uses them.

6Build your own security operations center

Time: an evening. You learn: SIEM, log collection, alerting.

What you need

  • A machine with at least 4 GB of free memory for Wazuh. Wazuh supports Arm servers, so it can run on your cloud server; if memory is tight, run it in a virtual machine on your PC instead.

Steps

  1. Install Wazuh with the all-in-one quickstart.
  2. Install the Wazuh agent on your cloud server and on your lab machines.
  3. Create a webhook in a private Discord server, and send Wazuh alerts to it through Wazuh's external API integration.
  4. Test it: try a few wrong SSH passwords against your own server, or run a scan from Kali, and wait for the alert.

What you should see

  • Alerts in the Wazuh dashboard and in Discord for failed logins, scans and file changes.

If it breaks

  • The dashboard is slow or stops: Wazuh needs memory. Stop other containers or move it to your PC.

You just learned

  • How security teams collect logs from many machines, turn them into alerts, and get notified in time to act.

7Beat a machine with no hints

Time: one to three evenings. You learn: the full methodology, from discovery to full control.

Steps

  1. Download a beginner machine from VulnHub or HackMyVM.
  2. Import it into VirtualBox on your internal network, never on a bridged or NAT network.
  3. Work through the methodology: find the machine on the network, list its services, research each one, gain a foothold, then escalate to administrator.
  4. Keep notes as you go: what you tried, what failed and why.
  5. Only read a walkthrough after you have finished or been stuck for a long time, and then compare it with your notes.

You just learned

  • How to approach an unknown system on your own, the single most important skill in offensive security.

8Build an AI with a secret, then break it

Time: an evening. You learn: how language models follow instructions and why prompt injection works.

Steps

  1. Install Ollama and download a small model your PC can run.
  2. Create a custom model with a system prompt containing a made-up password and the rule never to reveal it. The Modelfile documentation shows how.
  3. Try to get the password out: role-play, ask for it in another language, ask for a story or an acrostic poem, or ask it to repeat its instructions.
  4. Strengthen the instructions and attack again. Then try a defense outside the model, such as filtering its answers for the password.

You just learned

  • Why instructions alone cannot protect secrets in an AI app, and why real systems keep sensitive data out of the model's reach.

9Waste attackers' time with an SSH tarpit

Time: thirty minutes. You learn: how automated attackers behave.

Steps

  1. Create one of the two small AMD virtual machines included in Oracle's Always Free tier.
  2. Move that machine's real SSH login to another port, then install Endlessh on port 22. It sends an endless, slow SSH banner, so connecting bots wait for a login that never comes.
  3. After a day, read its log, which records how long each connection lasted.

You just learned

  • That most attacks are automated, and that defenders can make them slower and more expensive.

10Final project: attack your own lab and catch yourself

Time: an evening. You learn: how attack and defense fit together.

Steps

  1. Install the Wazuh agent on a modern Linux target in your lab, and run a deliberately weak service on it.
  2. From Kali, run a full attack against it: discovery, scanning, access and escalation. Write down the time of each step.
  3. Switch sides. Open Wazuh and find each step in the alerts and logs.
  4. For every step Wazuh missed, find out why, and add or tune a rule so it would be detected next time.

You just learned

  • How an attack looks from both sides, and how detection is built and improved: the daily work of a security team.

Optional extras

  • Split your lab into separate networks with an OPNsense firewall virtual machine.
  • Self-host a password manager with Vaultwarden, reachable only through your VPN.
  • Capture your lab traffic with Wireshark while you attack it.
  • Run a capture-the-flag competition for friends with CTFd.

Staying safe and legal

  • Only test systems you own or have written permission to test. Practice targets exist so you never need anyone else's.
  • Keep vulnerable machines on internal networks only.
  • Download tools only from the official sites linked in this workbook.
  • Shut down cloud resources you no longer use.
